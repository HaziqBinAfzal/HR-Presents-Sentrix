# Sentrix Developer Guide

## Application structure

Sentrix uses a Flask application factory in `app.py`, a primary blueprint in `analyzer/routes/main.py`, SQLAlchemy models in `models.py`, WTForms in `forms.py`, analyzer modules under `analyzer/`, and reusable workflow services under `helpers/`.

## Request flow

A browser request enters Flask, is dispatched to the main blueprint, validated through forms or route logic, authorized against the current user, and delegated to helper services. Analysis services invoke syntax, lint, complexity, formatting, security, and optional AI modules. Results are persisted through SQLAlchemy and may be transformed into reports or downloadable artifacts.

## Blueprints and routes

Keep routes focused on HTTP concerns: input validation, authentication, authorization, status messages, redirects, and response rendering. Move archive handling, analysis orchestration, report generation, and review logic into service modules. Use consistent endpoint names and avoid importing application globals in ways that create circular dependencies.

## Models

Models represent users, projects, analyses, reviews, settings, and related records. Every user-owned record must have an explicit ownership relationship and every query returning a user-owned object must enforce that ownership. Add indexes for frequently filtered foreign keys and timestamps after measuring query behavior.

## Services and helpers

Services should accept explicit inputs, return structured results, and raise domain-specific errors rather than rendering templates. File-producing services should use controlled directories, collision-resistant names, atomic writes where possible, and cleanup on failure.

## Authentication and authorization

Flask-Login handles session identity. Authentication proves who the user is; authorization must still verify that the user may access the requested project, analysis, report, review, or settings record. Never trust an ID from a URL or form without an ownership query.

## Analysis pipeline

A safe pipeline should:

1. Validate upload metadata and size.
2. Store the original upload outside the public web root.
3. Extract archives with path traversal and resource-limit protection.
4. Discover supported files.
5. Run analyzers with timeouts and isolated error handling.
6. Normalize findings into a stable internal schema.
7. Persist status and results transactionally.
8. Generate reports only from authorized records.
9. Clean temporary files according to retention policy.

## Adding an analyzer

Create a focused module under `analyzer/` with a small public interface, deterministic output schema, timeout behavior, and tests for valid, invalid, empty, and hostile input. Register it in the orchestration service, document dependencies and configuration, and ensure one analyzer failure does not silently mark the entire project clean.

## Creating a route

Add the route to an appropriate blueprint, apply authentication where required, validate method and form data, load resources through ownership-filtered queries, delegate business logic, handle expected failures, and add tests for unauthorized, forbidden, missing, invalid, and successful cases.

## Reports and exports

Reports should be generated from persisted, authorized data rather than trusting client-submitted findings. Escape or sanitize untrusted content for the target format. Apply output size limits, stable filenames, and content-disposition headers. Record enough metadata to identify which analysis produced the artifact.

## Database changes

Use Flask-Migrate/Alembic for schema evolution. Review autogenerated migrations manually. Test upgrades and downgrades, data backfills, nullable transitions, uniqueness constraints, and large-table behavior. Do not rely on `db.create_all()` for production upgrades.

## Testing strategy

- Unit tests for analyzers, validators, and pure helpers
- Integration tests for routes, database behavior, mail stubs, reports, and exports
- Authorization tests for every user-owned resource
- Archive and upload abuse tests
- Migration tests from representative prior schemas
- End-to-end smoke tests for critical account and analysis journeys

## CI/CD

A production pipeline should install from a clean environment, verify formatting, run lint and security checks, run tests with coverage, validate migrations, build deployment artifacts, scan dependencies and images, and deploy only immutable reviewed commits. Secrets must come from the CI secret store and must not be printed.

## Coding standards

Use clear naming, small functions, consistent formatting, explicit exceptions, context managers for files, and parameterized database operations. Keep configuration outside source code. Document security-sensitive choices. Avoid duplicate CSS/JavaScript and template logic by extracting shared components.

## Local debugging

Development debug mode may be used only on a trusted local machine. Never expose the debugger to a network. Reproduce issues with sanitized fixtures and include traceback, route, interpreter version, dependency state, and exact commit when reporting a bug.
